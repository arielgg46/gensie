# 06 Heterogeneous Self-Consistency

## Purpose of This Section

This note supports the paper section on Mixed-SC, the submitted heterogeneous self-consistency pipeline. The final paper should explain why DRILLER uses multiple extractor styles, how trials are generated, and how schema-aware aggregation combines candidate outputs. Mixed-SC is not a judge pipeline and does not ask another model call to adjudicate candidates. It uses deterministic heuristic aggregation over postprocessed JSON predictions.

## Why Self-Consistency Is Used

Generative extraction can be unstable. Even with a fixed schema and prompt, different generations may differ in enum choices, array cardinality, string spans, null decisions, or nested object boundaries. In GenSIE, these differences matter because the output is evaluated field by field after schema flattening. A single incorrect field can reduce precision or recall, and array errors can affect several flattened values.

Self-consistency is a common inference-time strategy for reducing variance. The basic idea is to generate multiple candidate answers and then select or aggregate the answer supported by the candidates. However, a naive version that repeats the same prompt may reinforce the same systematic bias. If the prompt tends to over-fill nullable fields, repeated samples may simply produce different hallucinated values. If it tends to omit array items, repeated samples may not recover them.

DRILLER's Mixed-SC uses self-consistency in a heterogeneous way. It combines two extractor styles: direct Schema-RAG and reasoning-augmented Reasoned-RAG. The intent is to obtain candidates with complementary error profiles. Direct extraction can be shorter and more structurally direct; reasoning-augmented extraction can spend tokens on evidence analysis before committing to values. The aggregator then combines the final-shape outputs.

## Heterogeneous Rather Than Repeated Prompting

The submitted Mixed-SC pipeline requests four trials:

- two Schema-RAG-style trials;
- two Reasoned-RAG-style trials.

The intended sequence is interleaved: reasoned, direct, reasoned, direct. Each trial independently performs the full extraction process. This includes RAG retrieval, prompt construction, strict structured generation, JSON parsing, deterministic cleanup, and reasoning unwrapping when applicable.

This is different from sampling the same prompt four times. The trials are heterogeneous at the extractor level. Reasoned trials use a reasoned prompt schema and temporary reasoning/value wrappers. Direct trials use the plain Pydantic-style schema and final-value output format. Both styles use RAG, but the examples are rendered according to the active extractor. Thus, candidate diversity comes from both sampling and methodological variation.

The final paper should describe the four trials as "requested" because runtime budget logic may cap allowed trials. The source notes indicate a budget planner with token and time estimates. The submitted spec requests four, but the runner may stop when the allowed-trial estimate is reached. A careful wording is: "Mixed-SC requests four trials, subject to runtime budget limits."

## Candidate Shape Before Aggregation

Aggregation receives final-shape JSON candidates. This is an important design point. Reasoned-RAG trials do not pass raw `{reasoning, value}` objects to the aggregator. They are unwrapped first. All valid candidates therefore share the original target schema shape.

This simplifies aggregation and keeps it aligned with the evaluator. The aggregator can recursively traverse the target schema and compare candidate values at each field. It does not need to reason about extractor-specific wrapper formats. It also means that reasoning strings do not affect voting or clustering directly; they only influence the values generated by reasoning-augmented trials.

Invalid trials are excluded. A trial can be invalid if JSON parsing fails, if wrapper unwrapping fails, or if it returns an error-like record rather than a usable output. If all trials are invalid, the aggregator returns an error record rather than fabricating an extraction. The final paper can mention this as a conservative failure behavior.

## Recursive Schema-Aware Aggregation

Mixed-SC uses recursive schema-aware aggregation. The aggregator does not treat candidate objects as opaque strings and does not simply choose the most common complete object. Instead, it descends through the target schema and combines values according to their type.

This matters because complete-object agreement is unlikely for complex JSON outputs. Two candidates may agree on most fields but differ in one array item or one enum. Selecting a whole candidate would discard useful agreement at other fields. Recursive aggregation lets the system preserve consensus where it exists and handle uncertain fields locally.

The aggregation strategy can be summarized by schema type:

- exact scalar types use exact matching or voting;
- strings use schema-aware lexical similarity and clustering;
- nulls are counted separately with cautious support logic;
- objects are aggregated field by field;
- arrays are aggregated by clustering items and selecting a candidate array;
- arrays of objects can use identity-like fields for item matching.

## Scalars: Enums, Booleans, Numbers, and Simple Values

For exact scalar types such as enums, booleans, integers, and numbers, aggregation groups values by canonical equality. This is appropriate because these types are evaluated rigidly: an enum label must match exactly, a boolean is either correct or incorrect, and numeric/date-like values often have exact expected forms depending on the schema. The selected value is the one with strongest support under the voting/clustering logic.

For free strings, exact matching is too brittle. Two candidates may extract semantically equivalent or nearly identical spans with small differences in punctuation, casing, accents, or surrounding context. DRILLER therefore uses string similarity for clustering. The default string similarity is lexical: it normalizes strings, removes diacritics, lowercases, collapses whitespace, and combines exact normalized equality, token multiset F1, and character 3-gram F1. The source notes give weights of `0.15`, `0.45`, and `0.40`, respectively, and a default scalar string threshold of `0.78`.

The final selected representative for a scalar cluster is a medoid: a value actually produced by one of the candidates whose average similarity to the others in the cluster is highest. This is conservative because it avoids synthesizing a new string that no trial generated. It also avoids over-normalizing values beyond what the schema or source text supports.

## Null Support Logic

Null handling is deliberately cautious. Null is counted as a separate candidate value. For nullable fields, null wins only when its support is strictly greater than the support of the best non-null cluster. A tie does not default to null.

This logic reflects the asymmetry of grounded extraction. Returning null when a value is present loses recall, while returning a value when evidence is absent creates a hallucination. Neither error is harmless. The strict-greater-than rule avoids making null an easy fallback in ambiguous cases. It requires a stronger candidate consensus for null than for a tie.

The paper should connect this to the GenSIE setting, where null values are used to test grounding but are intentionally not supposed to be exploited by always returning null. DRILLER's aggregation mirrors that balance: null is supported when candidates agree that evidence is absent, but it does not automatically override plausible non-null evidence.

## Object Aggregation

Objects are aggregated field by field. This allows the system to combine agreement across candidates even when complete nested objects differ. For each object property, the aggregator applies the appropriate value-type logic recursively. Required root fields are handled as part of the schema. Optional non-root properties are included only when their support meets the configured threshold.

Field-by-field aggregation is important for nested schemas. Candidate A may correctly extract a date while Candidate B correctly extracts a label. If the object were selected wholesale, one of these correct values might be lost. Recursive aggregation can retain both if each has support at its field position.

However, field-wise aggregation has a trade-off. In arrays of objects, independently aggregating fields without respecting item identity could create invalid hybrids. DRILLER addresses this through array item clustering and identity-like field detection, discussed below.

## Array Aggregation

Arrays are not aggregated by position. GenSIE list evaluation is order-insensitive, and extraction outputs may list items in different orders. DRILLER therefore clusters items across candidate arrays.

The array aggregation process can be described conceptually as:

1. collect observed arrays from valid candidates;
2. deduplicate very similar items within a single trial so one trial cannot cast multiple votes for duplicates;
3. cluster items across trials using schema-aware item similarity;
4. generate candidate final arrays from supported clusters;
5. select an array using a recall-biased MBR-style criterion.

The source notes indicate a within-trial deduplication threshold of `0.96`. They also describe support floors of `2` and additional ratio-derived support floors based on `0.40`, `0.50`, and `0.60` of observed arrays. Original observed arrays are not included as candidates by default. These details can be included if space permits, but the final paper should focus on the rationale: array aggregation should recover items supported across trials while avoiding duplicates and unsupported hallucinated items.

## Arrays of Objects and Identity-Like Fields

Arrays of objects require matching items that refer to the same entity or event. DRILLER optionally detects an identity-like field inside the object schema. Candidate identity fields are scored using signals such as whether the field is required, whether it is a free string, and whether its name or description resembles an identity-bearing attribute such as `name`, `title`, `entity`, `mention`, `source`, `ingredient`, `symptom`, or `reaction`. Fields that look like attributes rather than identities, such as `label`, `category`, `type`, `probability`, `severity`, `amount`, `unit`, `date`, `year`, `count`, `number`, or numeric/boolean/enum fields, are penalized.

When a suitable identity field is selected, item clustering can use identity-string similarity to group object items that refer to the same underlying item. The source notes give a default identity-string threshold of `0.62`. This helps prevent the aggregator from merging two different objects merely because their non-identity attributes are similar, and it helps align attributes from the same named item across trials.

The paper should present this as a heuristic, not a guarantee. Some schemas may lack a clear identity field, and some object arrays may require matching by multiple fields. The heuristic is designed for robustness across variable schemas without manual schema-specific rules.

## Recall-Biased MBR-Style Array Selection

After clustering array items, DRILLER selects a final array using a recall-biased MBR-style selector. Candidate arrays are scored by similarity to observed arrays. The selector uses a tolerance around the best score; among candidates within that tolerance, it prefers the longest array, then the higher-scoring one, then the earlier candidate.

The source notes give a default MBR tolerance of `0.06`. The effect is to prefer recall when candidate arrays have similar expected utility. This design choice reflects a common array failure mode: models may omit items. If a longer supported array is nearly as well supported as a shorter one, choosing the longer array can improve recall without accepting arbitrary unsupported items.

The final paper should avoid overstating this as universally optimal. It is a heuristic tuned to the structured extraction setting, where missing list items are common and order is irrelevant. It can also introduce false positives if clusters are too permissive or if repeated hallucinated items appear across trials.

## Schema-Aware Similarity

The aggregation system uses schema-aware similarity for non-exact values. String similarity is lexical by default. Object similarity is field-weighted: the source notes indicate higher weights for strings, enums, numeric, and boolean fields, somewhat lower weight for arrays, and neutral weight for other fields. Missing fields do not contribute similarity when only one object has the field.

Array similarity uses a greedy bipartite matching style over item similarities and computes a Jaccard-like score:

```latex
\mathrm{sim}(A,B) = \frac{\sum \mathrm{matched\ item\ similarities}}{|A| + |B| - \sum \mathrm{matched\ item\ similarities}} .
```

This is not necessarily the exact formula to print in the final paper unless verified, but it captures the source-note description: matched item similarities contribute to overlap, and the denominator penalizes missing or extra items.

## Failure Modes and Trade-Offs

Mixed-SC can improve robustness in principle, but it also has trade-offs. It uses more model calls and more tokens than single-pass extraction, especially because two trials include reasoning strings. It depends on candidate diversity; if all trials share the same error, aggregation cannot fix it. If trials produce different hallucinations, clustering may select a wrong value with apparent support. If string similarity thresholds are too permissive, distinct values can be merged; if too strict, equivalent spans can fail to cluster.

Array aggregation has its own risks. A recall-biased selector may include extra items when several candidates over-extract similarly. Identity-field detection may choose a poor identity field for unusual schemas. Field-by-field aggregation can combine values from different candidates in ways that no single trial produced, which is useful for independent fields but risky when values are correlated.

The final paper should present Mixed-SC as a principled heuristic response to variance, not as a perfect correction mechanism. It is schema-aware, deterministic after candidate generation, and designed to combine complementary extractor styles, but it remains limited by candidate quality and schema ambiguity.

## Claims to Make and Avoid

Safe claims:

- Mixed-SC requests four trials: two direct Schema-RAG-style and two Reasoned-RAG-style.
- Each trial performs retrieval, prompting, strict generation, and postprocessing independently.
- Aggregation receives final-shape JSON candidates.
- The aggregator is recursive and schema-aware.
- Scalars, strings, nulls, objects, arrays, and arrays of objects have different aggregation behavior.
- The final mixed pipeline uses heuristic aggregation, not judge aggregation.

Claims to avoid unless supported later:

- Do not claim self-consistency improved performance without official evidence or ablations.
- Do not describe judge or verdict-judge aggregation as submitted.
- Do not imply that aggregation can recover information absent from all candidates.
- Do not claim the pipeline always ran all four trials if budget caps may reduce trial count.
